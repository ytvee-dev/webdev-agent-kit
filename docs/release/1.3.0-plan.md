# 1.3.0 Issue 71 Implementation And Release Plan

This document records the plan and checks for the version in its title. For
current setup, use the [installation guides](../install/README.md); for changes
by version, see the [changelog](../../CHANGELOG.md).

## Goal And Boundaries

Address the remaining portable rules and documentation gaps in issue #71 after
1.2.0. Preserve 21 skills, nine Claude agents, existing client contracts, host
configuration and Apache-2.0. No OpenCode work. Design-system work is a draft
for owner testing on a real project, not a verified synchronization feature.
The owner confirmed drafts and requested a new follow-up issue for field testing.
The original host's Codex activation and real Figma fidelity require external
field evidence; source or synthetic checks cannot close those acceptance gates.

## Responsibilities

The primary maintainer acts sequentially as release owner, repository analyst,
instruction architect, documentation editor, React rule auditor and validation
engineer. A fresh independent reviewer checks the final material rule changes.
The project owner evaluates draft design-system contracts on a real project;
that feedback belongs in a later release.

## Acceptance Criteria

- AC-01: role-selection instructions name real wiki pages, preserve the current
  task and permissions, and distinguish conversational roles from model routing.
- AC-02: design-source acquisition has one explicit default and a documented
  precedence rule for an explicitly selected designer role; incomplete evidence
  remains unknown and read-only intake cannot authorize source writes.
- AC-03: every recommendation in the pinned Vercel React inventory has an audit
  disposition and a reason. Shipped rules respect installed versions, the
  existing data stack, sensitive cache boundaries and measured performance.
- AC-04: design-system sketches define source authority, component/token
  mappings, change boundaries and field evidence, clearly marked experimental.
- AC-05: Figma effect inspection records the contributing layers, effect stack,
  bindings, state and visual evidence; prepared scenarios expose missing values
  without claiming that a real design has been inspected or fixed.
- AC-06: current documentation removes open-source participation positioning,
  retains maintenance/release instructions and leaves the license unchanged.
- AC-07: all six targets, schemas, graph links, context budgets, helper tests,
  lint, archives and existing client contracts pass. Live checks remain separate.
- AC-08: a reviewed PR passes CI, the exact merged commit is tagged, the release
  workflow succeeds, and downloaded published archives pass checksum/extraction.

## Sequential Work

### S-01 Scope And Evidence [AC-01..AC-06]

1. Read issue #71 and its comments, current source, release evidence and wiki.
2. Pin the Vercel rule inventory and inspect the full referenced rule files.
3. Distinguish implemented Codex activation from host-specific trust/runtime
   checks; avoid changing a working bootstrap merely to close an issue.
4. Record draft-only scope and publication boundaries before implementing.

### S-02 Documentation And Roles [AC-01, AC-06]

1. Replace obsolete Custom-instructions links with the exact frontend/designer
   pages and a client-neutral role-selection guide.
2. Define explicit selection, task continuity, unavailable-page fallback and
   the difference between a role, a skill, a native subagent and a model.
3. Remove community recruitment language; retain a maintainer change process,
   support/evidence reporting and security guidance as needed.
4. Preserve Apache-2.0 text and metadata; do not label the code proprietary.
5. Run link/schema/source checks for this slice.

### S-03 React Performance Audit [AC-03]

1. Audit each pinned rule against current owners and concrete applicability.
2. Group missing high-impact guidance into a compact conditional reference:
   request waterfalls, bundle boundaries, server/client work and render cost.
3. Keep installed TanStack/SWR conventions; do not mandate new dependencies.
4. Gate framework-specific APIs on current official documentation and versions.
5. Reject blanket cache, memo, hydration-warning suppression or micro-optimization
   prescriptions. Preserve authorization and per-user/per-tenant isolation.
6. Connect the reference to the React profile and affected implementation/review
   workflows with conditional loading. Prepare realistic and near-miss evals.
7. Check inventory coverage and changed skill contracts before proceeding.

### S-04 Design Intake And Drafts [AC-02, AC-04, AC-05]

1. Align source-inspection, capability and authoring rules with explicit role
   preferences while keeping the generic fallback and security boundaries.
2. Describe effect acquisition across ancestors, instances and overrides;
   distinguish blur types, opacity scope, clipping and effect order.
3. Define evidence required before translating effects into CSS or assets;
   unknown properties must not silently become zero or invented exact values.
4. Provide draft design-system inventory, component/token mapping and a pilot
   protocol. No automatic synchronization, new writing tools or native role.
5. Add prepared scenarios for role precedence, incomplete effect evidence,
   source conflicts and opt-in draft work using the existing evaluation runner.
6. Provide a field-feedback form with reproducible context, expected/actual
   behavior and sanitized evidence for a later release.

### S-05 Verification And Independent Review [AC-01..AC-07]

1. Run scoped skill/schema/link/budget checks after each owning slice.
2. Align version metadata and changelog for 1.3.0; build all targets.
3. Run the full validation orchestrator, existing lint and archive checks.
4. Prepare new scenarios across supported targets; report preparation and
   synthetic checks separately from authenticated behavioral evaluation.
5. Check archive exclusion/preservation and stable/versioned checksum equality.
6. Give the complete diff, acceptance criteria and evidence to a fresh reviewer.
7. Repair required findings; rerun affected checks and obtain repair review.

### S-06 Publication [AC-08]

1. Commit the complete source change, open a PR with exact evidence and limits.
2. Wait for all PR checks, including Windows helper regressions.
3. Merge the reviewed head; verify the merged tree matches that head.
4. Create v1.3.0 from the merged commit and run the existing release workflow.
5. Download all published artifacts, verify SHA256SUMS and extracted fixtures.
6. Report release/PR links and the field checks reserved for the owner. Do not
   close all of issue #71 on the strength of static validation.
